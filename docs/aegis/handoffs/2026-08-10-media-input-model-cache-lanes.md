## 二、已经达成的共识

```text
一份追加式 canonical 会话历史
        │
        ▼
每次请求复制历史并按当前有效媒体能力投影
        │
        ├─ 可发送：原媒体
        └─ 不可发送：固定“媒体未发送”文本
```

“有效媒体能力”是媒体种类、消息位置、模型语义能力与提供方实际传输能力的交集。目录中有 `video_in` 不等于适配器一定能发送视频，也不等于视频能放进工具结果。

缓存采用模型车道：

```text
会话目录标识 + 提供方实例标识 + 模型标识 + 静态请求投影形状
```

不要把历史、媒体字节、本轮输入或随回合变化的尾部放入缓存键。不同模型不承诺共享缓存；回到同一车道时才复用最长稳定前缀。

## 四、必须先证明的风险

1. 支持视频模型读取视频并产生 N 个后续回合后，切到无视频模型时，N 个回合必须原样保留；只有视频部件变成固定说明。
2. 再切回支持视频模型时，只有仍在活动上下文内的视频可以重新出现；越过压缩边界后只保留稳定来源说明，重新读取必须追加新工具交换。
3. 旧的完整 `ReadMediaFile` 工具调用和结果必须作为历史重放。每个提供方都要用请求测试证明合法；若协议不能接受未在当前工具表声明的历史调用，只能在该提供方请求副本中完整转换“助手调用加全部匹配结果”为稳定文本。
4. 工具结果媒体与用户媒体必须分开验证。只支持用户媒体的协议，只能在完整工具交换之后投影附加用户媒体消息，不能插入交换内部。
5. 缺失 Blob 必须得到确定性不可用说明，不能构造空媒体；不可发送媒体绝不读取或编码 Blob。
6. 目录能力和传输能力必须按媒体种类和消息位置交叉计算；没有实际传输路径时不得暴露相应工具能力。
7. 内联视频必须使用有界读取和资源测试；不能靠 Kimi 的 100MB 文件限制推导 Neo 的内存安全。
