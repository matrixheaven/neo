# TUI Mouse Text Selection Design

## Status

The user approved the design direction in three sections on 2026-08-07:

1. selection owners and product boundaries;
2. event flow, copying, and invalidation;
3. acceptance, retirement, and residual risk.

This written design still requires user review. Product source changes and the
implementation plan remain separate authorization boundaries.

This design extends the single fullscreen transcript direction recorded in:

- `docs/aegis/adr/ADR-0012-fullscreen-transcript-document.md`;
- `docs/aegis/baseline/2026-08-04-fullscreen-transcript-document.md`.

It does not create a second transcript document, viewport, renderer, terminal
lifecycle, or compatibility path.

## Problem

Neo captures mouse input for its fullscreen TUI, so ordinary left-button text
selection is application-owned. Selection is currently implemented in only
three places:

- `DocumentSelection` selects transcript text in document coordinates;
- `PromptState` selects editable chat-input text in character coordinates;
- `TodoSelection` selects rendered Todo rows in screen coordinates.

Every other visible region lacks application-owned text selection. This
includes BTW content, pending-input previews, completion lists, footer text,
standalone dialogs, rich dialogs, Task Browser, and Theme Manager.

The missing coverage is generated by shared routing and rendering gaps rather
than by 23 independent dialog defects:

1. The interactive controller offers events to blocking transcript entries,
   Task Browser, and rich dialogs before the ordinary mouse path. Task Browser
   and rich dialogs report the event handled even when their inner state
   ignores left-button press, drag, and release.
2. `NeoTui::handle_mouse_event` rejects selection when a prompt-blocking
   overlay is focused, except for approvals and questions.
3. Fullscreen overlays return from the render path before `last_layout` is
   updated, so the final visible frame has no hit map for selection.
4. Normal chrome rows classified as `ChromeRowKind::Other` are ignored.
5. A transcript gesture is routed by the pointer's current row instead of by
   the gesture's press owner. Dragging from the transcript into chrome prevents
   the final release from reaching `TranscriptPane` and makes downward edge
   auto-scroll unreachable through the real application route.

Adding selection to every dialog would preserve this recurrence generator.
New interfaces would continue to require coordinated changes in event routing,
layout metadata, selection state, painting, copy priority, and tests.

## Confirmed Outcome

Every currently visible, non-secret TUI text surface supports application-owned
left-button selection without per-interface selection code.

The three coordinate domains remain intentionally distinct:

- transcript selection remains document-coordinate and keeps cross-entry
  selection, semantic keyboard copy, double-click word selection, and edge
  auto-scroll;
- chat input remains a real editable character selection with caret, delete,
  and replacement behavior;
- all other visible text uses one final-frame selection that copies the exact
  rendered cells currently visible to the user.

Only one selection may be active at a time. A gesture keeps the owner chosen at
press time until release, even when the pointer crosses another region.

Overlay input fields do not gain mouse editing. They remain keyboard-edited,
while their rendered visible text can be selected and copied through the final
frame. Masked values expose only their rendered mask.

## Goals

- Make normal chrome, standalone overlays, rich dialogs, Task Browser, and
  Theme Manager selectable through one final-frame path.
- Ensure new rendered surfaces inherit selection without registering their
  overlay type in another selection match.
- Keep transcript and chat-input semantics unchanged.
- Fix transcript cross-region release and downward edge auto-scroll at the
  gesture owner.
- Keep highlight cells and copied cells identical.
- Preserve Unicode grapheme integrity and ANSI styling while painting.
- Keep clipboard routing centralized and preserve the current `Ctrl+C` exit
  protection.
- Delete Todo-specific selection ownership instead of retaining both old and
  new paths.
- Work on macOS, Linux, and Windows without platform-specific selection logic.

## Non-goals

- Adding mouse activation for buttons, list items, tabs, choices, or dialog
  submission.
- Making overlay text fields mouse-editable.
- Selecting or copying hidden, off-screen, clipped, or scrolled-out overlay
  content.
- Adding final-frame drag auto-scroll to dialogs or overlays.
- Changing transcript card bodies, copy semantics, expansion semantics, or
  entry ordering.
- Changing Delegate, DelegateGroup, DelegateSwarm, or Workflow card layout.
- Changing approval, question, tool execution, session persistence, model
  context, provider requests, or cache-prefix bytes.
- Changing raw SGR parsing, mouse queue coalescing, terminal mouse capture, or
  terminal-native Shift-drag ownership.
- Adding a selection settings surface, compatibility branch, or fallback
  renderer.

## Product Risk Lens

### Downsides

- Final-frame selection copies visual rows, so wrapping and visible decoration
  are copied as displayed rather than reconstructed into source semantics.
- A dynamic row changing during selection must invalidate that selection to
  avoid copying text different from the highlight.
- Starting a gesture in the transcript and starting one in surrounding chrome
  intentionally produce different behavior because only the transcript owns
  an unbounded document and edge auto-scroll.
- Real graphical-terminal mouse and clipboard behavior cannot be fully proven
  by headless tests.

### Benefits

- Coverage follows final rendering rather than an overlay inventory.
- The fix removes Todo-only state and copy branches.
- Dialog implementations remain unaware of text selection.
- Hidden secrets cannot leak because selection sees only rendered cells.
- New interfaces become selectable without changing the input controller.

### Decision

The user selected visible-text selection for overlay fields rather than full
mouse-editable field selection. The downsides above are accepted.

## First-Principles Decision

### Invariants

- Any non-secret text the user can currently see can be selected and copied.
- Highlight and clipboard text must refer to the same visible cells.
- Only one selection owner is active at a time.
- Transcript and chat input retain their existing specialized semantics.
- No hidden value may enter a derived final-frame text map.

### Assumptions Removed

- A selectable component does not need its own mouse handler.
- A new overlay does not need to be added to a selection allowlist.
- Todo does not need a selection owner inside `NeoChromeState`.
- The pointer's current region does not determine who receives the rest of an
  already-open gesture.

### Smallest Sufficient Path

Promote the existing rendered-row selection concept from Todo into one
`FrameSelection` owned by `NeoTui`, reuse the existing cell slicing and ANSI
selection painting helpers, and delete the Todo-specific path.

Do not replace `DocumentSelection` or `PromptState` selection. They solve
different coordinate domains and behaviors.

## Existence And Architecture Integrity

### Existence Check

- Proposed surface: final-frame text map and `FrameSelection` state.
- Existing reuse candidate: Todo screen coordinates, transcript cell slicing,
  ANSI selection painting, final frame composition, and centralized clipboard
  writing.
- Why the existing Todo surface is insufficient: it stores only Todo-local
  coordinates and frozen text in `NeoChromeState`; it cannot describe
  standalone or fullscreen overlays.
- Creation proof: the final composed frame is the only surface containing every
  visible region. A single derived map there removes all per-overlay selection
  branches.
- Entropy impact: Todo-specific state, painting, materialization, and copy
  priority are deleted.
- Decision: add the final-frame helper by promoting and replacing the Todo
  path, not alongside it.

### Architecture Integrity

- Invariant: one active selection produces one matching highlight and copy.
- Canonical owners: `TranscriptPane` for transcript documents, `PromptState`
  for editable chat input, and `NeoTui` for the final visible frame.
- Responsibility overlap to remove: `TodoSelection` and Todo copy fields in
  `NeoChromeState`.
- Higher-level simplification: selection events reach `NeoTui` before overlay
  input handlers, while wheel events keep their current focused-surface route.
- Falsifier: if any selectable overlay still needs selection-specific code,
  the final-frame design has failed and must be revised instead of adding an
  exception.
- Verdict: proceed and update ADR-0012 plus its landed baseline only after
  implementation and focused verification.

## Alternatives

### Per-interface selection

Add selection state, hit testing, painting, and copy behavior to each dialog
and overlay.

Rejected because it duplicates behavior across 23 overlay variants, requires
every future surface to opt in, and leaves the two shared routing defects
unchanged.

### One final-frame selection for everything

Replace transcript and prompt selection with a single screen-coordinate
selection.

Rejected because it loses transcript edge auto-scroll and stable document
coordinates, semantic keyboard copy, editable prompt selection, and caret
behavior.

### Selected hybrid

Keep the two specialized semantic selections and add one final-frame visual
selection for every other surface. This is the only option that gives automatic
coverage without discarding existing correct behavior.

## Selected Architecture

### 1. Three Disjoint Selection Owners

`NeoTui` routes a press to one of three owners:

```text
Transcript
Prompt
Frame
```

The owner is chosen from the most recently rendered frame:

- a press in the transcript body chooses `Transcript`;
- a press in an editable chat-input content row chooses `Prompt`;
- every other visible row chooses `Frame`.

The owner is stored for the open gesture. Drag and release always return to
that owner, independent of the pointer's later region.

A new press clears selections owned by the other two domains. A plain click in
a final-frame region leaves no selection after release. A plain prompt click
keeps its existing caret placement behavior.

### 2. Final Frame Text Map

Both ordinary frames and fullscreen overlay frames pass through one final step
before they are returned to the renderer. That step derives a `FrameTextMap`
from exactly the rendered lines that will be shown, after the application
gutter has been added and before selection paint is applied.

The map contains:

- frame width and height;
- rendered ANSI rows before selection paint, including the final screen-column
  offset introduced by the application gutter;
- corresponding plain visible rows with ANSI, hardware cursor markers, and
  non-visible control sequences removed;
- row ownership for press routing;
- focused-surface identity sufficient to detect overlay replacement.

The map is derived presentation state. It never enters `TranscriptStore`,
session JSONL, model context, provider requests, compaction, or cache-prefix
bytes.

Fullscreen overlays no longer return before recording this map. Their rows are
all `Frame` rows. Standalone and rich overlays also produce `Frame` rows, while
any transcript rows still visible behind an approval or question remain
`Transcript` rows.

No `OverlayKind` selection match is added.

### 3. Frame Selection State

`FrameSelection` stores only what final-frame selection requires:

- anchor row and display cell;
- active row and display cell;
- tentative press time and movement state;
- materialized visible text after release;
- selected plain-row snapshots used to validate later frames;
- frame dimensions and focused-surface identity.

It reuses the existing movement threshold, long-press delay, cell slicing, and
ANSI background painting behavior. It does not own scrolling, widget state,
or overlay actions.

The module is independent of dialog types. `NeoTui` owns the state and supplies
the latest final-frame map.

### 4. Gesture Routing

Selection mouse events are recognized before Task Browser and rich-dialog
input handling:

1. Shift-modified events bypass Neo as they do now.
2. Wheel events follow the existing focused-surface behavior and are not sent
   through final-frame selection.
3. Left/right press, drag, and release reach `NeoTui` first.
4. `NeoTui` routes the complete gesture to the press owner.
5. A selection event is not offered to an overlay after Neo has handled its
   selection semantics.

This ordering does not add mouse activation to any control. It only prevents
selection events from being silently consumed.

Approval and question keyboard ownership stays unchanged. Their visible
transcript cards remain selectable through `TranscriptPane`.

### 5. Transcript Boundary Repair

When a transcript gesture is open, pointer rows below the body are still sent
to `TranscriptPane` as out-of-body document coordinates rather than rerouted
to chrome.

This makes the existing downward auto-scroll condition reachable. The release
also always reaches `TranscriptPane`, closing the gesture even when the pointer
ends over Todo, prompt, footer, an overlay boundary, or the terminal edge.

The transcript selection implementation remains the sole owner of transcript
anchor, active endpoint, auto-scroll, word selection, and materialization.

### 6. Prompt Boundary

Chat-input selection keeps `PromptState` character indices and edit behavior.
The prompt remains responsible for caret placement and selected-range edits.

Dragging outside prompt rows stays within the prompt owner's coordinate
boundary and release always closes the prompt gesture. This design does not
extend prompt selection behavior to overlay fields.

### 7. Painting And Materialization

Selection painting occurs after final frame composition, gutter application, and
cursor-marker extraction, and before the frame is returned to the differential
renderer.

For each selected row:

- calculate the inclusive visual range from anchor and active endpoints;
- clamp it to the rendered row's display cells;
- apply the existing theme selection background while preserving foreground
  styles and restoring selection background after ANSI resets;
- never split a Unicode grapheme, wide character, variation sequence, or
  zero-width-joiner sequence.

On release, copy materializes from the same plain rows and display-cell ranges.
It preserves visible row breaks. It does not reconstruct source tabs or remove
visible borders and decorations because the user selected visual text.

An isolated empty range produces no copy value. Blank rows between selected
text rows preserve their newline.

### 8. Frame Changes And Invalidation

A final-frame selection remains valid only while its selected visual cells
still describe the visible content.

Clear the frame selection and any open frame gesture when:

- frame width or height changes;
- the focused standalone/fullscreen surface changes;
- any selected row's plain content or display-cell mapping changes;
- the selected row disappears.

Changes outside the selected row range do not clear the selection. This avoids
losing a selection merely because an unrelated footer spinner or background
region changes.

Released transcript and prompt selections keep their existing invalidation
rules.

### 9. Copy Ownership

`NeoTui` exposes one current-selection query for controller-level copy:

1. transcript selection;
2. frame selection;
3. prompt selection.

Only one should be active, so the order is defensive rather than user-visible
priority.

`Ctrl+C` with any active selection copies through the existing asynchronous
clipboard writer and does not arm exit confirmation. Without a selection, the
current clear/exit behavior remains unchanged.

Right-click requests the current unique selection text through the same query
and collapses that selection after the request, matching current transcript,
prompt, and Todo behavior.

No new clipboard helper, platform command, timeout, or system process is added.

### 10. Sensitive And Non-visible Content

The final-frame map is derived only after each component has rendered its safe
display form. API keys, tokens, passwords, and similar fields therefore enter
the map only as masks already present on screen.

The selection path must never call dialog getters for raw values. A test must
prove that copying across a masked input returns only mask characters and does
not contain the raw secret.

Cursor markers, ANSI control sequences, image payload sequences, and other
non-visible terminal protocol bytes are removed from copy materialization.

## Surface Coverage

### Transcript-owned

- welcome, user, assistant, thinking, shell, approval, question, status, retry,
  MCP, goal, skill, instruction, Delegate-family, and Workflow entries;
- normal tool cards, grouped tools, expanded output, and document separators;
- approval and question cards while their keyboard state is focused.

### Prompt-owned

- editable chat-input content rows only.

### Frame-owned

- Todo panel title, items, and expand/collapse status;
- BTW panel content;
- pending steer, follow-up, and shell previews;
- completion and command lists rendered in chrome;
- prompt borders, prompt notices, shell-mode label, status text, and footer;
- session and model selection surfaces;
- model, provider, MCP, and workspace management surfaces;
- confirmation, trust, choice, workflow, help, and input dialogs;
- custom endpoint and registry flows;
- Task Browser and all of its detail, answer, stop, and save views;
- Theme Manager list, status, and preview;
- any future visible final-frame row not classified as transcript body or chat
  input content.

Unreachable legacy overlay variants are not revived or changed by this work.
Their separate retirement is outside this task.

## Dynamic And Error Behavior

- A selection event arriving before the first rendered frame is ignored rather
  than guessed into a region.
- A release without an open gesture is a no-op.
- A malformed or unsupported mouse sequence remains the raw parser's concern;
  this design does not add fallback parsing.
- If clipboard writing fails, the internal selected text remains available as
  it does for current transcript selection.
- If selected final-frame content changes, the selection clears instead of
  copying stale or mismatched text.
- Opening or closing an overlay clears a frame selection whose surface identity
  no longer matches. Transcript and prompt selections are cleared only through
  the normal single-owner switch.
- Wheel input during frame selection keeps the focused surface's existing
  scrolling behavior; if selected rows change, the next frame invalidates the
  selection.
- Background transcript growth does not invalidate a frame selection unless it
  changes selected visible rows.
- Resize never attempts to translate final-frame coordinates. It clears the
  frame selection; transcript reflow remains document-owned.

## Retirement

### Delete-first declaration

- Deletion class: internal code retirement.
- Old path: `TodoSelection`, Todo selection fields in `NeoChromeState`, Todo
  paint/materialization helpers, Todo-specific gesture ownership, and Todo
  copy priority.
- New canonical owner: `NeoTui` final-frame selection.
- Preserved behavior: Todo text remains drag-selectable, highlighted, copied by
  right-click and `Ctrl+C`, and cleared when another owner starts.
- Retired behavior: Todo-only state and special routing.
- External boundary: none.
- Persistent data risk: none.
- User confirmation required: no; this is code retirement covered by the
  approved design.

### Retirement decision

Delete first. Do not leave aliases, compatibility fields, dual painting, or a
Todo fallback. A lingering production reference is a failed retirement check.

## Complexity Boundary

Current pressure signals:

- `app.rs` is already over 600 lines after prompt/Todo selection wiring;
- transcript `selection.rs` is already over 800 lines;
- interactive `input.rs` is over 1,600 lines.

Governance:

- put final-frame selection state and pure row/cell operations in one focused
  module;
- keep `app.rs` limited to final-frame recording, painting, and owner routing;
- add only a small selection-event pre-route to interactive `input.rs`;
- remove Todo state and helpers from chrome owners;
- do not move transcript document selection into the new module;
- place broad final-frame behavior in a focused integration-test target rather
  than growing already oversized general shell test files.

The new module is justified because it replaces an existing owner and prevents
new responsibility from being added to three already pressured files.

## Acceptance Matrix

### Owner routing

- Transcript press, drag into chrome, downward edge auto-scroll, and release
  remain one transcript gesture.
- Prompt press retains caret/edit selection and always receives release.
- A press on any other visible row starts final-frame selection.
- A new press clears prior selections from other owners.
- Shift-modified drag bypasses Neo unchanged.

### Normal frame

- Todo text selects through the final-frame owner with no Todo-specific state.
- BTW, pending-input preview, completion rows, notices, and footer are
  selectable.
- Prompt content remains prompt-owned while its border is frame-owned.

### Overlay frame

- One representative standalone overlay proves the standalone render path.
- One representative rich dialog proves the rich-dialog path.
- Task Browser proves fullscreen overlay routing and selection.
- Theme Manager proves the other fullscreen overlay renderer.
- Approval and question focused states continue selecting their transcript
  cards rather than creating a parallel overlay selection.

### Copy and invalidation

- `Ctrl+C` copies frame selection before clear/exit behavior.
- Right-click uses the same materialized text and collapses the selection.
- Resize, selected-row change, and surface replacement clear frame selection.
- An unrelated changing row does not clear frame selection.
- Clipboard failure does not silently change the selected text.

### Text fidelity and privacy

- ASCII, CJK wide characters, combining marks, emoji sequences, variation
  selectors, and zero-width joiners paint and copy as complete graphemes.
- ANSI resets do not drop the selection background inside the chosen span.
- Cursor markers and terminal protocol sequences do not enter copied text.
- A masked secret copies only the displayed mask.
- Visual wrapping and selected blank rows produce the approved visible-row
  copy semantics.

### Compatibility

- Existing transcript keyboard and mouse selection tests remain valid.
- Existing prompt editing selection remains valid.
- Delegate-family card fixtures remain unchanged.
- Approval/question input, Task Browser keyboard input, dialog keyboard input,
  and wheel behavior remain valid.
- Print, pipe, export, `neo run`, and non-TTY resume remain static and do not
  construct final-frame selection state.

## Verification Strategy

Use the smallest exact tests that prove each distinct behavior. Do not create
one duplicate test per overlay variant because variants share the same final
frame owner.

Expected focused proof groups:

1. pure final-frame selection state and Unicode cell behavior;
2. `NeoTui` normal-frame routing and painting;
3. standalone, rich, and fullscreen overlay frame composition;
4. interactive controller pre-routing, `Ctrl+C`, right-click, and wheel
   preservation;
5. transcript cross-region release and downward auto-scroll;
6. masked-value negative proof;
7. lingering Todo-selection reference check;
8. frozen Delegate-family and context-integrity boundaries where touched code
   could plausibly affect them.

Every Rust command must name one package, one target selector, and a test-name
filter. Test discovery must confirm each filter selects at least one test.
Formatting and `git diff --check` remain separate mechanical checks.

## Native Validation

After focused local proof:

1. validate the real graphical mouse highlight, right-click, `Ctrl+C`, resize,
   overlays, and Shift-drag path on the macOS host;
2. check host memory, boot only the Fedora VM, run the focused native tests and
   real-PTY lifecycle smoke, then shut it down;
3. check host memory, boot only the Windows VM, run the focused native tests and
   terminal lifecycle checks, then shut it down.

One VM may run at a time. Automated PTY acceptance does not prove system
clipboard side effects or graphical mouse behavior. A Windows graphical smoke
requires a logged-in desktop session and remains explicit residual risk when
that environment is unavailable.

## Compatibility Boundary

- `TranscriptStore`, `DocumentLayout`, `TranscriptPane`, `FullscreenTerminal`,
  `LiveRenderer`, and `FrameScheduler` remain the existing owners.
- No transcript entry, card renderer, Delegate-family body, or Workflow group
  is redesigned.
- Tool authorization, execution, scheduling, persistence, and timing do not
  change.
- Canonical system/user/assistant/tool history remains append-only.
- Provider request projection, context cache prefix, compaction, micro
  compaction defaults, and snip/dedup defaults do not change.
- Raw mouse parsing and queued event ordering do not change.
- Clipboard platform commands and deadlines do not change.
- Terminal alternate-screen and mouse-capture enter/restore behavior does not
  change.
- Cross-platform code uses existing portable text/cell helpers with no new OS
  branch.

## Task Intent And Impact Summary

- Outcome: every visible non-secret surface is selectable without per-screen
  selection branches.
- Stop condition: no implementation completion claim until focused local,
  native platform, retirement, and residual-risk evidence is assembled.
- Affected layers: interactive input routing, final-frame composition,
  selection state, clipboard selection query, focused tests, ADR/baseline sync.
- Non-goals: mouse control activation, overlay mouse editing, hidden-content
  selection, transcript/card redesign, context or execution changes.
- Primary risks: gesture misrouting, highlight/copy mismatch, secret leakage,
  dynamic-frame invalidation, and platform-specific terminal behavior.

This document is an advisory design record. It does not claim implementation,
verification, release readiness, or completion.
