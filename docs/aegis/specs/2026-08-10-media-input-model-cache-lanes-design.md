# Neo 图片与视频输入、模型投影和缓存车道设计

日期：`2026-08-10`

状态：待用户审阅

## 1. 目标与结论

Neo 增加图片和视频读取能力，同时允许同一会话切换支持图像、支持视频、同时支持两者或不支持多媒体的模型。

唯一推荐路径是：

```text
持久化原始媒体记录
        │
        ▼
按当前模型能力和提供方传输能力生成请求投影
        │
        ├─ 可发送：发送原媒体
        └─ 不可发送：发送稳定的媒体未发送说明
```

持久化历史只有一份。模型、提供方和媒体投影变化只影响当前请求副本，不得写回会话。

缓存目标不是让不同模型共享同一前缀，而是为同一会话维护可复用的模型车道：

```text
会话标识 + 提供方标识 + 模型标识 + 静态媒体请求形状
```

车道键不包含历史消息、媒体字节或本轮新增内容，否则每轮都会产生新键，失去前缀缓存的价值。

## 2. 已确认基线

- `neo-agent-core` 的请求消息顺序是系统提示、工作区上下文、上下文消息副本；媒体解析和工具交换修复发生在请求副本上。
- 当前 `Content` 只有文本、思考和图像；`neo-ai::ContentPart` 也只有图像媒体分支。
- 当前 `ModelCapabilities` 只有 `images`，模型能力解析不认识视频。
- 当前不支持图像时，运行时在请求前直接报错；这会阻止“已有图像历史切到无图像模型”。本设计将其改为请求投影中的确定性说明。
- 当前 `prompt_cache_key` 只取会话目录名，并通过 `RequestOptions.session_id` 传给部分提供方。
- Kimi 新版会随模型能力刷新媒体工具，但其会话缓存键仍未按模型或媒体投影分车道；Kimi 的高效视频上传仅属于其特定提供方路径，不是通用视频能力。
- 当前工作树已有与本任务无关的 Rust 改动：`.gitignore`、`crates/neo-agent/src/main.rs`、交互层 Git 状态文件及其测试。后续不得纳入本任务。

## 3. 需求就绪检查

- 需求来源：用户要求 Neo 支持图片和视频，并能安全处理多媒体能力不同的模型切换。
- 用户场景：支持视频模型读取视频后继续多个回合，再切到不支持视频的模型；随后可以切回原模型。
- 硬约束：会话历史追加式、缓存前缀不被改写、没有 Kimi 专属上传协议、跨平台、内存有界。
- 成功标准：历史记录字节不变；每种模型得到合法且诚实的请求；同一车道回访时静态前缀保持一致；超限媒体在发送前确定性失败。
- 非目标：跨模型缓存命中、自动抽帧、远端媒体服务、用户维护多个缓存副本、重写旧会话格式。
- 结论：`ready`。

## 4. 数据模型

### 4.1 Canonical 媒体

在 `neo-agent-core` 中使用一套媒体引用类型承载图像和视频：

- `Content::Image { mime_type, data }`
- `Content::Video { mime_type, data }`
- 两者共用 `MediaRef::{Blob, Base64, Url}`。

`Blob` 是首选持久化形式，字节写入会话目录的 Blob 存储并以摘要引用。历史消息只保存类型、媒体类型和摘要引用，不保存临时绝对路径。

在 `neo-ai` 中增加对应的视频内容部件，并让图像与视频共用同一种数据引用表达。旧的 `ImageRef` 只作为迁移前的源码名称处理；确定新所有者后不保留双轨别名。

### 4.2 能力与传输

模型语义能力增加 `videos`。提供方适配器另外声明实际可用的传输模式，并按消息位置区分：

- 用户消息中的图像和视频：内联、网址、提供方正式文件引用或不支持；
- 工具结果中的图像和视频：原位媒体、结果后的附加用户消息或不支持。

有效能力是“媒体种类、消息位置、模型语义能力、适配器传输能力”的交集。目录只声明“模型愿意接收”，不能单独使视频工具可用。

## 5. `ReadMediaFile` 行为

工具处理文件读取、类型识别、大小校验和 Blob 持久化，工具结果返回结构化媒体内容；它不负责决定当前模型是否能接收该媒体。

工具暴露根据有效能力生成：

| 有效能力 | 工具状态 | 参数和说明 |
| --- | --- | --- |
| 图像、视频 | 注册 | `path`；图像可选区域和清晰度参数；说明两种媒体都可读 |
| 仅图像 | 注册 | 只说明图像；视频路径执行时返回明确错误 |
| 仅视频 | 注册 | 只暴露 `path`；不出现图像专用参数 |
| 无 | 不注册 | 旧工具调用仍作为历史记录保留，但不能发起新的调用 |

当前请求没有媒体能力时，不在系统提示中额外注入长篇规则；工具表说明和执行错误负责当前工具语义。

## 6. 请求投影

请求构造先复制上下文消息，再执行一次有序的媒体投影。投影只产生临时消息，不写回 `AgentContext` 或 JSONL。

### 6.1 可发送媒体

当有效传输模式可发送时：

1. 先决定当前媒体在当前位置是否可发送；
2. 只有可发送时才从 Blob 读取字节或引用；
3. 交给对应提供方序列化器；
4. 发送图像或视频，并保留原始内容顺序。

视频内联必须采用有界读取和明确大小上限。不能同时长期持有原始字节、Base64 副本和完整请求副本。提供方不支持文件引用时，不得假装存在文件引用。不可发送媒体绝不读取或编码 Blob。

### 6.2 不可发送媒体

媒体部件替换为固定、可识别、与路径无关的文本。例如：

```text
[媒体未发送：视频，摘要 abc123；当前模型不支持视频输入。]
```

规则：

- 只替换媒体部件；同一工具结果中的文字、工具调用编号和其他内容保持不变；
- 使用摘要、类型和固定原因，保证同一模型车道每次生成完全相同的文本；
- 不声明媒体已经被模型读取；
- 缺失或损坏 Blob 也生成确定性的“媒体不可用”文本，不再生成空编码；
- 支持模型切回后重新从原始 Blob 投影媒体。

### 6.3 历史媒体工具交换

旧的 `ReadMediaFile` 工具调用和工具结果是历史事实，不因当前工具表没有该工具而删除。当前工具表只控制新工具调用。

媒体工具结果不得再被运行时压成纯文本。canonical 工具结果必须保存文字和结构化媒体部件，再由请求投影决定实际传输。

每个提供方必须有定点请求测试，证明它能重放带有历史媒体工具调用的完整交换。如果某个提供方协议不接受未出现在当前工具声明中的历史调用，适配器必须在请求副本中把“助手工具调用加上全部匹配结果”整体转换为稳定文字，不能留下孤立结果、删除一侧或拆开调用和结果。

当提供方支持用户视频但不支持工具结果视频时，完整工具交换仍保持原顺序；视频只能作为该交换之后的附加用户媒体消息投影，绝不插入到调用与结果之间。无视频能力时，该附加消息不存在，结果内只保留固定说明。

## 7. 缓存车道

为 `RequestOptions` 增加专用的提示缓存键字段，保留现有 `session_id` 的会话关联语义和请求关联用途。OpenAI 系列把新字段映射为 `prompt_cache_key`；现有 `x-client-request-id` 仍使用会话关联标识。Anthropic 不把该字段误作用户标识。

缓存车道由以下稳定身份组成：

```text
会话目录标识
+ 提供方实例标识
+ 模型标识
+ 协议、媒体消息位置、媒体传输方式和历史媒体工具交换的静态投影形状
```

它不包含：

- 历史消息内容；
- 媒体字节、临时路径或上传时间；
- 本轮用户输入；
- 每轮变化的输出字段。

工具表、系统提示和推理设置变化会自然改变提供方可见前缀；媒体能力或历史工具交换投影变化必须改变静态请求投影形状，避免把不同请求误认为同一车道。

模型切换的实际效果：

```text
模型甲读视频并完成 N 个回合
        │
        ▼
切到不支持视频的模型乙
        │
        ├─ 原始历史：视频仍存在
        ├─ 乙的请求：视频部件变成固定说明，N 个回合原样保留
        └─ 乙车道：命中切换前可共享的最长稳定前缀
        │
        ▼
切回模型甲
        │
        ├─ 甲的请求：恢复原始视频部件
        └─ 甲车道：复用离开甲之前的稳定前缀，乙期间消息是新尾部
```

不承诺跨提供方或跨模型命中缓存；只能承诺车道身份和投影稳定。

## 8. 提供方边界

- 提供方序列化器必须显式处理图像和视频，不能把未知媒体静默丢弃。
- 当前不支持视频的协议在有效能力计算阶段被标记为不可发送；不会因目录误报而发送空字段。
- 不接入 Kimi 的专属上传端点、文件标识或协议扩展。
- 对正式支持标准文件引用的提供方，可以在后续独立任务增加传输实现；本设计只要求能力声明和安全拒绝边界。
- OpenAI、Anthropic、Google 等适配器分别用请求行为测试证明媒体部件、历史工具交换和错误路径。

## 9. 自审查与反例结论

### 9.1 历史是否被改写

不会。媒体替换发生在请求消息副本；工具调用、工具结果、N 个后续回合及其顺序仍来自同一份 canonical 历史。会话恢复仍只追加新事件。

### 9.2 切回支持模型是否能恢复视频

仅当媒体仍在活动上下文中时能恢复。压缩边界之外的原始消息不会因切换模型被重新注入请求；否则既破坏当前压缩语义，也使已缓存前缀发生回退。压缩后的派生上下文必须保留稳定的媒体来源说明，但不重新发送原字节。用户需要重新查看时，支持媒体的模型必须新调用 `ReadMediaFile`，从而追加新的历史事件。

### 9.3 不支持模型是否会误以为看过视频

不会。固定说明明确写出“未发送”和“当前模型不支持”，并保留摘要标识；后续文字结论仍可使用，但模型不能重新观察视频。

### 9.4 历史工具调用是否会使请求失效

设计不删除历史交换；各适配器必须验证其合法性。若协议确实不接受，适配器只在请求副本中转换完整交换为文本，不能由运行时随意删掉一侧消息。工具结果媒体和用户媒体也分别验证，不把“模型支持视频”误当作“工具结果能够传视频”。

### 9.5 缓存键是否反而损害命中率

不会把每轮历史放进键。键只隔离真实不同的模型、提供方和静态媒体形状；同一车道追加新消息后，提供方仍有机会复用最长共同前缀。

### 9.6 视频读取是否击穿内存目标

设计拒绝无界内联。读取、编码和请求组装必须有上限并避免多份长期副本；无法满足上限时在调用提供方前返回明确错误。

### 9.7 是否复制了 Kimi 的不完整行为

没有。Kimi 的动态工具刷新只作为行为参考；其专属上传、会话级缓存键和部分图像降级缺陷不纳入 Neo。

## 10. 验收标准

1. 图像、视频、双能力和无能力四种工具表均与有效能力一致。
2. 支持视频模型完成读取后追加 N 个回合，切到不支持视频模型时，请求包含固定说明、完整 N 个回合和合法历史工具交换。
3. 媒体仍在活动上下文时，切回支持视频模型会恢复原始视频；越过压缩边界后只保留稳定来源说明，重新读取会追加新的媒体工具交换。所有情况下 canonical JSONL 和 Blob 字节比较完全相同。
4. 同一模型车道的静态请求形状和媒体说明在 A→B→A 序列中保持稳定；缓存键不随历史增长。
5. 所有支持的提供方都覆盖用户媒体、工具结果媒体、视频不支持、缺失 Blob、历史工具交换、压缩边界和大小超限错误分支。
6. 超限媒体不发起提供方请求，不生成空编码，不保存超出内存上限的请求副本。

## 11. ADR 信号

这是持久化媒体表达、请求投影所有者、提供方能力边界和缓存键语义的架构决定。实现完成后应将本设计、工作记录和验证证据用于 ADR 回填；本轮不创建新的兼容双轨。
